# 20. Database Migrations with Alembic

A quick reference and revision guide for managing database schema evolution using Alembic in FastAPI.

---

## 1. What Did We Do?
We integrated **Alembic** to version-control and apply database schema changes safely:
1. Installed Alembic: `uv add alembic`.
2. Initialized the Alembic directory: `uv run alembic init alembic`.
3. Configured `alembic/env.py` to point to `settings.DATABASE_URL` and `Base.metadata`.
4. Generated an autogenerated migration:
   `uv run alembic revision --autogenerate -m "create users and tasks tables"`.
5. Applied the migration: `uv run alembic upgrade head`.
6. Removed `Base.metadata.create_all()` from `main.py` so schema changes are handled exclusively through migrations.

---

## 2. Why Did We Do It?
- **Zero Data Loss**: In production, you can never drop or delete a live database (`rm database.db`) when adding columns or tables. Migrations apply `ALTER TABLE` changes while preserving all existing user data.
- **Git for Your Database**: Every change to your models is captured as a timestamped Python script with an `upgrade()` and `downgrade()` function committed to version control.
- **Team & Deployment Consistency**: CI/CD pipelines, staging, and production servers run `alembic upgrade head` to automatically apply all pending schema changes.

---

## 3. How Does It Work?

```
1. You modify models in Python (e.g. models/user.py, models/task.py)
                           │
                           ▼
2. Run: uv run alembic revision --autogenerate -m "description"
                           │
                           ▼
3. Alembic compares your live database tables against Base.metadata
                           │
                           ▼
4. Generates a migration script in alembic/versions/
   • def upgrade():   commands to apply changes
   • def downgrade(): commands to roll back changes
                           │
                           ▼
5. Run: uv run alembic upgrade head
                           │
                           ▼
6. Alembic applies the SQL changes and updates the alembic_version table
```

## 4. Key Troubleshooting Lesson: Package Resolution in `alembic/env.py`

When using a `src/` layout project structure, ensure `alembic/env.py` adds `src` to `sys.path`:

```python
import sys
from pathlib import Path

# Add src to sys.path so taskflow_api package is properly resolved
sys.path.insert(0, str(Path(__file__).resolve().parents[1] / "src"))

from taskflow_api.config import settings
from taskflow_api.database import Base
from taskflow_api.models import task, user

target_metadata = Base.metadata
config.set_main_option("sqlalchemy.url", settings.DATABASE_URL)
```

> **Why this matters**:
> If models import `from taskflow_api.database import Base`, but `alembic/env.py` imports `from src.taskflow_api.database import Base`, Python treats them as **two different `Base` classes**. Alembic would see 0 tables in metadata and attempt to drop your tables!
> Always import `Base` using the identical package path.

## 5. Daily Alembic Cheat Sheet

| Command | Purpose |
| :--- | :--- |
| `uv run alembic revision --autogenerate -m "message"` | Detect model changes and generate a migration script |
| `uv run alembic upgrade head` | Apply all pending migrations to the database |
| `uv run alembic downgrade -1` | Roll back the last migration |
| `uv run alembic current` | Display the current migration revision hash |
| `uv run alembic history` | List all migration scripts in chronological order |
